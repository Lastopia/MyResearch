# 代码设计

## 设计目的

本文档用于约束本项目后续代码的编写方式，可作为研究代码实现时的本地 skill 使用。项目目标：{{一句话研究目标}}。

代码应服务于快速、清晰、可复现实验，而不是追求复杂工程化包装。默认使用者是研究者本人，因此代码应尽量模块化、精简、直观，避免冗余的安全检查和过度抽象。

## 核心原则

### 模块化与精简

代码应尽可能模块化，把数据处理、模型/主体逻辑、训练流程、评估逻辑、配置管理和工具函数拆开。每个模块只负责自己的职责，避免把大量逻辑塞进一个脚本里。

同时，代码应保持精简，只保留当前实验真正需要的抽象和功能。不提前设计复杂框架，不写暂时用不到的通用接口。

### 默认输入可信

本项目代码主要由研究者本人使用，因此默认输入是可信且合理的。实现时不需要加入大量冗余的安全性检查、边界检查或防御式编程逻辑；只在缺少检查会显著影响调试定位、实验复现或结果可靠性时，才添加必要的断言或简短校验。

### 命名约定

代码级命名统一使用简写：`base` 表示 baseline，`std` 表示 standard，不使用完整的 `baseline`、`standard`。其余机制/模块简写：{{列出本项目统一简写表，如 attn=attention、ffn=feed-forward}}。

## 总体结构

项目根目录优先采用以下结构：

```text
main.py
cfg.py
cfg预设.md
data/
output/
pipeline/
tools/
model/
```

`main.py` 是交互式控制台入口，负责解析命令、查看和修改当前配置、按顺序运行 pipeline 阶段。`cfg.py` 提供默认配置。`cfg预设.md` 用来保存可复制到控制台中的 `set ...` 参数预设。`data/` 存放全局共享数据资源。`output/` 存放每个 task 的运行结果。`pipeline/` 存放实验阶段。`tools/` 存放跨阶段复用的小工具。`model/` 存放模型结构和机制变体（如项目无模型训练，可将 `model/` 替换为 {{主体逻辑目录名}}）。

## 配置设计

`cfg.py` 负责提供实验启动时的默认配置，但不是唯一配置入口。执行 `main.py` 后，用户可以在控制台中临时修改配置。

`cfg.py` 中不同部分应使用不同字典管理，所有配置字典命名统一小写：

```python
run = {}      # 跨阶段共享参数：task、models、seed、device、dtype
model = {}    # 主体规模/结构参数
models = {}   # 所有模型(或方案)别名对应的机制组合
# 以下为各 pipeline 阶段专属字典，按本项目阶段增减：
data = {}
train = {}
{{stage}} = {}
```

`run["models"]` 是本次 task 要运行的模型别名列表。`model` 管理规模参数。`models` 中每个别名只保留机制组合字段，每个机制字段本身是一个字典，`name` 表示机制类型，其余键值对表示该机制自己的参数：

```python
models = {
    "base": {
        "attn": {"name": "std"},
        "ffn": {"name": "std"},
        "loss": {"name": "ce"},
    },
    "topk_attn": {
        "attn": {"name": "topk", "k": 64},
        "ffn": {"name": "std"},
        "loss": {"name": "ce"},
    },
}
```

模型规模不写进 `models`，避免机制组合和参数量大小混在一起。需要切换规模时，直接修改 `model`。本项目的机制维度为：{{如 attn / ffn / loss，按项目替换}}。

`output/{task}/config.json` 应按 `cfg.py` 中原本的配置结构保存，而不是扁平化保存。每个阶段运行结束后，应将该阶段实际使用的完整配置写入 `output/{task}/config.json`，保留完整上下文，而不是只保存被修改过的局部参数。

## 控制台命令

`main.py` 应设计成轻量交互式控制台。执行 `main.py` 后进入等待用户输入的界面，用户可以通过命令查看配置、临时修改配置，并运行指定 pipeline 阶段。这样在服务器端跑实验时，不需要每次为了小参数修改都改代码再同步到服务器。

控制台命令采用如下形式：

```text
run {stage}                # 运行指定阶段；run all 按默认顺序运行全部
run {stage1} {stage2} ...  # 按输入顺序连续运行多个阶段

cfg all | cfg {stage}      # 查看当前全部/某阶段配置

set run key=value ...      # 修改 run，例如 set run task=test1 models=base,topk_attn seed=42
set {stage} key=value ...  # 修改某阶段配置，key 必须严格匹配，不存在则报错，未提及的保持原样
set models {alias} ...     # 修改某模型别名的机制配置，支持点号路径：attn.name=topk attn.k=64

check gpu                  # 检查可用 GPU 并写入 run["gpus"]
clear {stage}              # 清理指定阶段产物（必须显式指定 stage）
help
exit
```

### GPU 状态输出

`check gpu` 用精简格式返回每张 GPU 的总显存、已使用显存和是否可用，显存统计应包含已被框架预分配或保留的部分：

```text
[GPU1] : (已使用显存)/(总显存)   status = available
[GPU2] : (已使用显存)/(总显存)   status = not available
```

除非用户明确要求，不输出 GPU 名称、核心数量、驱动版本等额外信息。`check gpu` 不只负责打印，还应把可用 GPU 写入当前内存配置 `run["gpus"]`，后续并行任务必须使用该列表分配，而不是重新枚举所有可见 GPU。面向用户显示时，GPU 编号从 `GPU1` 开始。

### 提示符与 task

控制台等待输入时，提示符中显示当前任务 `task`：

```text
[default] >
```

用户通过 `set run task=test1` 修改后，提示符同步变为 `[test1] >`。

### clear 命令

`clear` 必须显式指定要清理的 stage，禁止无参数 `clear` 默认清理全部结果：

```text
clear data
clear train
...
```

无参数 `clear` 只输出提示 `clear must specify stage name: {stage 列表}`，不得删除任何文件。涉及 checkpoint 的清理（如 `clear train`）只能删除当前 task 输出目录下的 checkpoints 和训练相关 metrics；其它 stage 只能清理各自阶段产物。

## 多 GPU 并行

多 GPU 并行的目标是"多个独立任务并行跑"，而不是默认做单个模型的数据并行或模型并行。并行单位是"模型别名 × seed"的独立任务，每个子进程绑定一个 GPU，并在日志中显示当前任务使用的 GPU。

由于 CUDA 不能在 fork 后重新初始化，多进程启动方式必须使用 `spawn`：

```python
ctx = multiprocessing.get_context("spawn")
```

CPU 线程数可根据调度器实际分配资源自动估计，但这只是每个进程的 CPU 线程数，不代表 GPU 分配。

## `data/`

`data/` 存放数据相关资源。资源应设计为独立于具体 task 的全局共享资源，不随某一次实验重复复制。每类资源都可以有多个版本，统一使用自定义简短别名作为文件夹名，并用 `meta.json` 记录真实来源、生成配置、依赖的上游资源别名和必要备注。具体实验任务不复制大体积共享数据，只在配置中引用对应别名。

本项目的资源类型为：{{按项目列出，例如 LM 项目为 raw / tokenizer / tokenized / blocks 四级}}：

```text
data/
    {资源类型1}/
        {alias}/
            meta.json
            ...
    {资源类型2}/
        {alias}/
            meta.json
            ...
```

## `output/`

`output/` 存放每次实验运行产生的结果，以 `task` 作为一级子目录：

```text
output/
    {task}/
        config.json
        checkpoints/   # 模型权重 + train.log 等过程日志（如适用）
        {{stage}}/     # 各阶段产物，按项目命名，如 sae/ metrics/ eval/ samples/
```

同一个 task 下可以包含多个 `model_alias`，输出目录不按 `model_alias` 再拆分子目录，所有模型变体共享同一个 task 输出结构，具体文件通过文件名携带 `model_alias` 区分。这样更方便在评估目录下生成跨模型合并图。

checkpoint 文件命名应包含 `model_alias`、seed 和 step，例如 `[base]seed42step20000.pt`；`best.pt` 可用于后续评估优先加载，但不能作为"训练已完成"的唯一依据。

### 复用与覆盖

当 `output/{task}/` 已经存在时，应优先复用昂贵训练产物：

- 训练类产物：如果已存在当前 `model_alias`（含 seed）对应的可用 checkpoint，默认跳过重复训练。跳过前必须读取 checkpoint 中的 `step`，只有 `checkpoint_step >= train.max_steps` 时才允许输出 `checkpoint exists` 并跳过；否则自动续训，从 `start_step + 1` 开始，并输出 `resume | step={旧} -> max_steps={新}`。只有当训练配置中 `retrain=true` 时，才允许强制重新训练。
- 中间产物（如分析模型、昂贵的派生结果）：复用条件应更严格。若别名相同但配置与依赖的上游产物不一致，不应静默覆盖；应使用新别名保存新结果，或返回提示让用户明确处理。
- 评估类结果：通常计算成本较低，可以直接覆盖已有结果。
- 除非用户显式设置或明确要求，代码不应自动删除、覆盖或清理已有 checkpoint。

续训保存的 checkpoint 应包含：`model`、`optimizer`、`scaler`、`cfg`、`step`、`alias`、`seed`。旧 checkpoint 如果缺少 optimizer 或 scaler 状态，应保持兼容：加载模型权重继续训练，但优化器和 scaler 可重新初始化。

## `pipeline/`

`pipeline/` 存放实验 pipeline 中的各个阶段。每个阶段写成一个独立 `.py` 文件，由 `main.py` 调用，文件名短而直观、统一小写、直接对应控制台中的阶段名称（适配服务器环境）。每个阶段文件暴露统一入口函数：

```python
def run(cfg):
    ...
```

`main.py` 只负责解析控制台命令、读取或修改配置，并按顺序调用对应阶段的 `run(cfg)`，不直接写入具体阶段的业务逻辑。

本项目阶段及默认顺序：{{如 data -> train -> sae -> attn -> eval，按项目替换}}。

## `model/`

`model/` 存放模型相关代码（非模型训练项目可替换为主体逻辑模块）。`model.py` 作为主体文件负责整体结构和前向流程；机制变体分文件存放，如 `attn.py`、`ffn.py`、`loss.py`（按本项目机制维度替换）。变体选择使用 `name` 字符串 + 参数字典，由 `model.py` 根据 `models[model_alias]` 选择实现。

## `tools/`

`tools/` 存放跨阶段复用的小工具函数，例如 json 读写、路径创建、配置打印、随机种子设置、checkpoint 加载、metrics 保存、资源占用统计等。工具函数应保持轻量、明确，不把项目做成复杂框架。

## 训练规范

`train` 配置字典中应包含训练过程控制参数：

```python
train = {
    "lr": {{}} ,
    "min_lr": {{}},
    "warmup_steps": {{}},
    "max_steps": {{}},
    "lr_schedule": "warmup_cosine",
    "log_interval": {{}},
    "eval_interval": {{}},
    "save_interval": {{}},
    "retrain": False,
}
```

`eval_interval` 和 `save_interval` 必须保持独立。评估只允许计算和记录指标，绝不能因为触发评估而保存 checkpoint；只有 `save_interval` 能决定什么时候保存 checkpoint。

训练应支持学习率调度，默认 `warmup_cosine`：warmup 升到目标学习率后 cosine decay 到 `min_lr`；保留 `constant` 作为特殊对照的可选项。

## 多 Seed

`run["seed"]` 应支持整数或整数列表。即使当前只跑一个 seed，文件命名和 metrics 也必须带 seed，避免未来多 seed 实验混淆，例如：

```text
[model_alias]seed42train.jsonl
[model_alias]seed42valid.jsonl
[model_alias]seed42summary.json
```

最终 eval 应支持按 seed 记录单次结果，并可按 model 聚合多 seed 均值。

## 日志规范

每个 pipeline 阶段开始时，在控制台输出醒目的阶段标题，方便在服务器日志中快速定位阶段边界：

```text
========== [{STAGE} START] ==========
```

训练类阶段应清晰跟踪进度。每次触发 `log_interval` 时，至少输出当前 GPU、model_alias、seed、step、train loss、耗时、内存占用和显存占用；每次触发 `eval_interval` 时，输出当前 valid loss。

日志必须使用固定列宽输出，保证不同模型名、step、loss、事件信息长度不同的时候，`|` 分隔符仍然纵向对齐。普通训练日志和事件日志必须共用同一套列宽：

```text
[train]  | GPU1   | base s42                       | step=2000                | train_loss=5.44                | valid_loss=6.32    | time=29s/85s       | mem=237.3/503G   | vram=8.4/45G
[train]  | GPU1   | base s42                       | checkpoint exists        | step=40000 >= max_steps=40000  |                    |                    |                  |
```

资源标签统一使用 ASCII 的 `mem` 和 `vram`，避免服务器终端中文编码异常。loss 保留两位小数；训练耗时按整秒记录，且按"同一个 SID 下的同一个模型和 seed"单独统计，切换模型或 seed 时不累计。已使用内存/显存应包含预分配但尚未真正写入数据的部分。

日志输出应精简、稀疏、结构化：保证关键字段完整的前提下，不输出冗余解释、复杂调试信息或大段文字。日志中直接显示 `model_alias`，不写 `model=`；不显示 task（提示符和输出目录已区分）。

## Metrics

`metrics/` 中按 step 产生的指标优先保存为 `.jsonl`，每行一个事件或 step；最终汇总保存为 `.json`：

```text
metrics/
    train.jsonl
    valid.jsonl
    {{stage}}.jsonl
    summary.json
```

## 评估与可视化

评估阶段应尽量生成图表来说明结果，而不仅保存原始数值。可视化应尽量合并同类项：优先按"同一个数据切分（SID）、同一个指标、不同模型"合并画在同一张图中，方便直观比较。只有当指标含义不同、SID 不同或合并后过于混乱时，才拆分成多张图。图表主要用于人工查看比较的，放在 `eval/` 中。
