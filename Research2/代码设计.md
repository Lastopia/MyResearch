# 代码设计

## 设计目的

本文档用于约束本项目后续代码的编写方式，可作为研究代码实现时的本地 skill 使用。项目目标是围绕 Transformer 的 `attn`、`ffn` 和 `loss` 等机制做对比实验，观察不同机制改动是否能诱导模型形成更稀疏、单义、可解释，并可能更适合 SAE 分解和因果干预的特征表示。

代码应服务于快速、清晰、可复现实验，而不是追求复杂工程化包装。默认使用者是研究者本人，因此代码应尽量模块化、精简、直观，避免冗余的安全检查和过度抽象。

## 核心原则

### 模块化与精简

代码应尽可能模块化，把数据处理、模型定义、训练逻辑、评估逻辑、配置管理和工具函数拆开。每个模块只负责自己的职责，避免把大量逻辑塞进一个脚本里。

同时，代码应保持精简，只保留当前实验真正需要的抽象和功能。不提前设计复杂框架，不写暂时用不到的通用接口。

### 默认输入可信

本项目代码主要由研究者本人使用，因此默认输入是可信且合理的。实现时不需要加入大量冗余的安全性检查、边界检查或防御式编程逻辑；只在缺少检查会显著影响调试定位、实验复现或结果可靠性时，才添加必要的断言或简短校验。

## 总体结构

项目根目录优先采用以下结构：

```text
main.py
cfg.py
cfg预设.md
data/
output/
pipeline/
tools/
model/
```

`main.py` 是交互式控制台入口，负责解析命令、查看和修改当前配置、按顺序运行 pipeline 阶段。`cfg.py` 提供默认配置。`cfg预设.md` 用来保存可复制到控制台中的 `set ...` 参数预设。`data/` 存放全局共享数据资源。`output/` 存放每个 task 的运行结果。`pipeline/` 存放实验阶段。`tools/` 存放跨阶段复用的小工具。`model/` 存放模型结构和机制变体。

## 配置设计

`cfg.py` 负责提供实验启动时的默认配置，但不是唯一配置入口。执行 `main.py` 后，用户可以在控制台中临时修改配置。

`cfg.py` 中不同部分应使用不同字典管理，所有配置字典命名统一小写：

```python
run = {}
model = {}
models = {}
data = {}
train = {}
sae = {}
attn = {}
```

`run` 管理跨阶段共享参数，例如 `task`、`models`、`seed`、`device`、`dtype`。其中 `run["models"]` 是本次 task 要运行的模型别名列表。`model` 管理模型规模参数，例如层数、头数、hidden size、FFN hidden size、block size 等。`models` 管理所有模型别名对应的机制组合。`data`、`train`、`sae`、`attn` 分别管理对应 pipeline 阶段的参数。

`models` 中每个模型别名只保留三个核心字段：

```python
models = {
    "base": {
        "attn": {"name": "std"},
        "ffn": {"name": "std"},
        "loss": {"name": "ce"},
    },
    "topk_attn": {
        "attn": {"name": "topk", "k": 64},
        "ffn": {"name": "std"},
        "loss": {"name": "ce"},
    },
}
```

模型规模不写进 `models`，避免机制组合和参数量大小混在一起。需要切换小模型或 GPT-2 small 级别模型时，直接修改 `model`。
每个机制字段本身是一个字典，`name` 表示机制类型，其余键值对表示该机制自己的参数。

代码级命名统一使用简写：`base` 表示 baseline，`attn` 表示 attention，`std` 表示 standard，不使用完整的 `baseline`、`attention`、`standard`。

`output/{task}/config.json` 应按 `cfg.py` 中原本的配置结构保存，而不是扁平化保存。推荐格式：

```json
{
  "run": {},
  "model": {},
  "models": {},
  "data": {},
  "train": {},
  "sae": {},
  "attn": {}
}
```

控制台中通过 `set` 修改的是当前内存配置。每个阶段运行结束后，应将该阶段实际使用的配置参数写入 `output/{task}/config.json`。配置保存应保留完整上下文，而不是只保存被修改过的局部参数。

## 控制台命令

`main.py` 应设计成轻量交互式控制台。执行 `main.py` 后，程序进入等待用户输入的界面，用户可以通过命令查看配置、临时修改配置，并运行指定 pipeline 阶段。这样在服务器端跑实验时，不需要每次为了小参数修改都改 GitHub 代码再同步到服务器。

控制台命令可以采用如下形式：

```text
run data
run train
run sae
run attn
run all
run data train sae

cfg all
cfg run
cfg model
cfg models
cfg data
cfg train
cfg sae
cfg attn

set run task=attn_topk_k16 models=base,topk_attn seed=42
set model n_layer=6 n_head=6 d_model=384 d_ff=1536 block_size=256 position_encoding=rope
set models topk_attn attn.name=topk attn.k=64 ffn.name=std loss.name=ce
set data block_size=128 blocks_alias=OpenWebText_GPT2_b128
set train lr=3e-4 batch_size=32
set sae sae_alias=layer4_exp8_l1_1e-3 hook_layer=4

check gpu
help
exit
```

`run {stage}` 用于运行指定阶段。`run all` 用于按默认顺序一键运行完整 pipeline，默认顺序为：

```text
data -> train -> sae -> attn
```

`run {stage1} {stage2} ...` 用于按输入顺序连续运行多个阶段，例如 `run data train sae`。如果数据已经准备好，可以手动运行 `run train sae attn` 跳过 `data` 阶段。

`cfg {stage}` 用于查看某个阶段实际使用的配置，`cfg all` 用于查看当前全部配置。`set {stage} key=value ...` 用于临时修改某个阶段的配置。参数名必须和对应配置字典中的 key 严格匹配：key 存在则更新，key 不存在则返回报错；没有出现在 `set` 命令中的其他参数保持原样。`set models {alias} ...` 用于修改某个模型别名对应的机制配置，并支持点号路径，例如 `attn.name=topk attn.k=64`。

`check gpu` 用于检查当前服务器可用 GPU，并用精简格式返回每张 GPU 的总显存、已使用显存和是否可用。显存统计应包含已经被框架预分配或保留的部分。输出必须避免冗余信息，优先采用如下格式：

```text
[GPU1] : (已使用显存)/(总显存)   status = available
[GPU2] : (已使用显存)/(总显存)   status = not available
```

除非用户明确要求，不输出 GPU 名称、核心数量、驱动版本等额外信息。

`help` 用于显示控制台支持的命令，`exit` 用于退出控制台。

控制台等待用户输入时，应在提示符中显示当前任务 `task`。默认任务可以是 `default`，提示符形式例如：

```text
[default] >
```

当用户通过 `set run task=test1` 修改任务后，提示符应同步变为：

```text
[test1] >
```

这样用户在服务器端交互时可以始终清楚当前操作对应哪个 task。

当 `check gpu` 检测到多张可用 GPU 时，后续运行 `run["models"]` 中的多个模型别名时，可以将不同模型分配到不同 GPU 上并行训练或评估，以提升整体实验效率。多 GPU 并行的目标是“多个独立模型变体并行跑”，而不是默认做单个模型的数据并行或模型并行。每个并行任务应明确绑定自己的 GPU，并在日志中显示当前任务使用的 GPU。面向用户显示时，GPU 编号从 `GPU1` 开始，而不是显示 `GPU0`。

## `data/`

`data/` 文件夹用于存放数据相关资源。`raw`、`tokenizer`、`tokenized` 和 `blocks` 都应设计为独立于具体 task 的全局共享资源，不随某一次实验重复复制。每类资源都可以有多个版本，并统一使用研究者自己定义的简短别名作为文件夹名。

```text
data/
    raw/
        {raw_alias}/
            meta.json
            ...
    tokenizer/
        {tokenizer_alias}/
            meta.json
            ...
    tokenized/
        {tokenized_alias}/
            meta.json
            tokens.bin
    blocks/
        {blocks_alias}/
            meta.json
            blocks.bin
```

`raw/` 存放原始数据集，例如 `OpenWebText/`。`tokenizer/` 存放 tokenizer 文件或配置。`tokenized/` 存放由某个 raw 数据和某个 tokenizer 生成的完整 token 序列。`blocks/` 存放由某个 tokenized 数据按指定 `block_size`、`stride`、切分方式等生成的训练样本块。

四类资源都应保持相同设计风格：用别名文件夹区分版本，用 `meta.json` 记录真实来源、生成配置、依赖的上游资源别名和必要备注。具体实验任务不复制这些大体积共享数据，只在配置中引用对应别名。

## `output/`

`output/` 文件夹用于存放每次实验运行产生的结果，以 `task` 作为一级子目录。

```text
output/
    {task}/
        config.json
        checkpoints/
        sae/
        metrics/
        eval/
        samples/
```

同一个 task 下可以包含多个 `model_alias`，每个 `model_alias` 对应一组具体的 `attn/ffn/loss` 机制组合。输出目录不按 `model_alias` 再拆分子目录，所有模型变体共享同一个 task 输出结构，具体文件通过文件名携带 `model_alias` 区分。这样更方便在 `eval/` 下生成跨模型合并图，而不是把评估结果拆散到多个模型子目录。

`checkpoints/` 存放所有模型变体训练过程中保存的模型权重，并同时存放 `train.log` 等训练过程日志。checkpoint 文件命名应包含 `model_alias` 和 step，优先采用 `[model_alias]step{step}.pt`，例如 `[topk_attn]step2000.pt`。`sae/` 存放该 task 下训练得到的 SAE 模型及其配置。`metrics/` 存放结构化指标。`eval/` 存放评估结果和主要合并图表。`samples/` 存放模型生成样例或用于人工检查的输出。

实验输出应按 task 聚合到同一个目录下，方便后续回看、比较和复现；大体积共享数据仍然只保存在 `data/` 下，`config.json` 只记录引用关系。

### 复用与覆盖

当 `output/{task}/` 已经存在时，应优先复用昂贵训练产物。如果 `output/{task}/checkpoints/` 中已经存在当前 `model_alias` 对应的可用模型 checkpoint，则 `run train` 默认认为该模型变体已经训练过，跳过重复训练。只有当 `train` 配置中的 `retrain=true` 时，才允许强制重新训练。

除非用户显式设置或明确要求，代码不应自动删除、覆盖或清理已有 checkpoint。评估类结果通常计算成本较低，可以直接覆盖已有结果。

SAE 训练结果默认复用，但复用条件应比模型 checkpoint 更严格。`output/{task}/sae/` 下可以按 `model_alias` 和 `sae_alias` 保存多个 SAE：

```text
output/
    {task}/
        sae/
            {model_alias}_{sae_alias}/
                config.json
                checkpoint.pt
                metrics.json
```

`sae_alias` 用于区分不同 SAE 类型或训练设置，例如不同 hook point、layer、hidden size、稀疏系数、训练步数或随机种子。运行 `run sae` 时，如果当前 `sae_alias` 下已经存在 checkpoint，并且其 `config.json` 与当前 SAE 配置及依赖的 base model checkpoint 一致，则默认复用该 SAE，不重复训练。如果配置不一致，不应静默覆盖旧 SAE；应使用新的 `sae_alias` 保存新结果，或返回提示让用户明确处理。SAE 的评估图表和 metrics 可以覆盖，因为它们通常可由已有 SAE checkpoint 重新生成。

## `pipeline/`

`pipeline/` 文件夹用于存放实验 pipeline 中的各个阶段。每个阶段写成一个独立 `.py` 文件，由 `main.py` 调用。

```text
pipeline/
    data.py
    train.py
    sae.py
    attn.py
```

`data.py` 负责数据准备阶段，包括 tokenizer、tokenized 数据和 blocks 的生成或选择。`train.py` 负责 base model 训练阶段。`sae.py` 负责 SAE 训练和 SAE 相关评估。`attn.py` 负责 attn 相关评估。阶段文件命名应短而直观，直接对应控制台中的阶段名称，并统一使用小写文件名以适配服务器环境。

每个阶段文件应暴露统一入口函数：

```python
def run(cfg):
    ...
```

`main.py` 只负责解析控制台命令、读取或修改配置，并按顺序调用对应阶段的 `run(cfg)`，不直接写入具体阶段的业务逻辑。

## `model/`

`model/` 文件夹用于存放模型相关代码：

```text
model/
    model.py
    attn.py
    ffn.py
    loss.py
```

`model.py` 作为模型主体文件，负责组织 Transformer 的整体结构和前向传播流程。除 attn、ffn 和 loss 函数之外，其他模型结构设计优先放在 `model.py` 中，例如 embedding、block 组织方式、residual 连接、LayerNorm 调用位置、输出头等。

`attn.py` 用于存放 attn 机制的不同变体，例如 std softmax attn、Top-k attn、阈值 attn 或其他稀疏化 attn。`ffn.py` 用于存放 FFN 机制的不同变体。`loss.py` 用于存放训练目标和 loss 函数的不同变体。

`model.py` 应通过 `cfg.py` 中的 `model` 控制模型规模参数，并通过 `models[model_alias]` 控制具体选用哪一种机制变体。变体选择优先使用简单字符串：

```python
models = {
    "topk_attn": {
        "attn": {"name": "topk", "k": 64},
        "ffn": {"name": "std"},
        "loss": {"name": "ce"},
    }
}
```

`model.py` 根据 `name` 选择对应实现，并根据 `model` 构建模型规模。这样可以在保持模型主体结构稳定的同时，方便后续通过控制台命令 `set models topk_attn attn.name=topk attn.k=64` 等方式直接切换机制变体。

## `tools/`

`tools/` 文件夹用于存放跨阶段复用的小工具函数，例如 json 读写、路径创建、配置打印、随机种子设置、checkpoint 加载、metrics 保存、资源占用统计等。工具函数应保持轻量、明确，不把项目做成复杂框架。

## 训练规范

`train` 配置字典中应包含训练过程控制参数，例如：

```python
train = {
    "lr": 3e-4,
    "min_lr": 3e-5,
    "warmup_steps": 1000,
    "max_steps": 100000,
    "lr_schedule": "warmup_cosine",
    "log_interval": 100,
    "eval_interval": 500,
    "save_interval": 2000,
    "retrain": False,
}
```

`log_interval` 控制每隔多少 step 输出一次训练日志。`eval_interval` 控制每隔多少 step 运行一次评估。`save_interval` 控制每隔多少 step 保存一次 checkpoint。`retrain` 控制当已有 checkpoint 存在时是否强制重新训练。

`eval_interval` 和 `save_interval` 必须保持独立。评估阶段只允许计算和记录指标，绝不能因为触发评估而保存 checkpoint；只有 `save_interval` 能决定什么时候保存 checkpoint。

训练阶段应支持学习率调度。默认使用 `warmup_cosine`：训练初期用 warmup 将学习率从较小值逐步升到目标学习率，随后使用 cosine decay 将学习率逐步衰减到 `min_lr`。同时保留 `constant` 作为可选项，用于简单 base 或特殊对照实验，但通常不作为首选。

## 日志规范

每个 pipeline 阶段开始时，都应在控制台输出醒目的阶段标题，用特殊符号形成明显分隔，方便在服务器日志中快速定位阶段边界。例如：

```text
========== [TRAIN START] ==========
========== [SAE START] ==========
========== [ATTENTION START] ==========
```

训练类阶段应尽可能清晰地跟踪进度，该规则同时适用于 base model 训练和 SAE 训练。每次触发 `log_interval` 时，至少输出当前 step、当前 train loss、已经训练耗时、内存占用和显存占用；每次触发 `eval_interval` 时，输出当前 valid loss。

loss 显示时优先保留两位小数。训练耗时按整秒显示和记录，不保留小数。训练耗时应按“同一个 SID 下的同一个模型和 seed”单独统计，一个模型训练结束后，切换到其他模型或其他 seed 时不累计前一个模型的时间。

内存和显存输出格式优先采用：

```text
内存: 已使用/总内存 | 显存: 已使用/总显存
```

已使用显存和内存应包含预分配但尚未真正写入数据的部分。只要资源已经被当前进程或框架分配、保留或实际使用，都应计入已使用数值中，方便在服务器上判断真实资源占用压力。

日志输出应尽可能精简、稀疏、结构化。在保证 GPU、model_alias、step、loss、耗时、内存、显存等关键信息完整的前提下，不输出冗余解释、复杂调试信息或大段文字。每条日志应尽量保持固定字段顺序和紧凑格式。日志中直接显示当前运行的 `model_alias`，不写 `model=`。日志中不需要显示 task，因为当前 task 已经显示在控制台提示符中，并且输出文件也通过 `output/{task}/` 区分。

日志格式可以采用类似形式：

```text
[train] GPU1 | topk_attn | step=1200 | train_loss=2.31 | valid_loss=2.45 | time=360s | 内存=12.4/64G | 显存=18.7/24G
```

如果某次日志没有 valid loss，控制台仍应保留该列的占位宽度，以保证所有 `|` 分隔符纵向对齐；结构化 metrics 中可使用 `null` 或省略字段。训练耗时也应被记录到 metrics 或日志中，用于后续比较不同模型、不同机制变体之间的训练效率。

## 当前实现补充规范

本节记录已经落实到代码中的最新设计，若与前文旧示例存在差异，以本节为准。

### 控制台清理命令

`clear` 命令必须显式指定要清理的 stage，禁止无参数 `clear` 默认清理全部结果，避免用户误把程序控制台命令与系统 `clear` 命令混淆。合法形式为：

```text
clear data
clear train
clear sae
clear attn
clear ffn
clear eval
```

如果用户只输入：

```text
clear
```

程序必须只输出提示：

```text
clear must specify stage name: data/train/sae/attn/ffn/eval
```

并且不得删除任何文件。`clear train` 会删除当前 `task` 输出目录下的 checkpoints 和训练相关 metrics；其它 stage 只能清理各自阶段产物。

### Pipeline 顺序

当前默认 stage 顺序为：

```text
data -> train -> sae -> attn -> ffn -> eval
```

`run all` 应按该顺序执行。`data` 阶段不使用 GPU；GPU 并行主要发生在 `train`、`sae`、`attn`、`ffn` 阶段。

### GPU 与多进程

`check gpu` 不只负责打印 GPU 状态，还应把可用 GPU 写入当前内存配置 `run["gpus"]`。后续并行训练或评估必须使用该列表分配任务，而不是重新用 `torch.cuda.device_count()` 盲目枚举所有可见 GPU。

多 GPU 并行的单位是“模型别名 × seed”的独立任务。每个子进程绑定一个 GPU。由于 CUDA 不能在 fork 后重新初始化，多进程启动方式必须使用 `spawn`：

```python
ctx = multiprocessing.get_context("spawn")
```

CPU 线程数可根据调度器实际分配资源自动估计，但这只是每个进程的 CPU 线程数，不代表 GPU 分配。

### Checkpoint 与续训

训练 checkpoint 文件名必须同时包含模型别名、seed 和 step，例如：

```text
[base]seed42step20000.pt
[base]seed42best.pt
```

`best.pt` 用于后续 SAE 和评估优先加载最佳模型，但不能作为“训练已经完成”的唯一依据。`run train` 判断是否跳过时，必须读取 checkpoint 中的 `step`，只有当：

```text
checkpoint_step >= train.max_steps
```

时才允许输出 `checkpoint exists` 并跳过训练。

如果已有 checkpoint 的 step 小于当前 `train.max_steps`，则必须自动续训：

```text
resume | step=20000 -> max_steps=40000
```

续训从 `start_step + 1` 开始。新保存的 checkpoint 应包含：

```text
model
optimizer
scaler
cfg
step
alias
seed
```

旧 checkpoint 如果没有 optimizer 或 scaler 状态，应保持兼容：加载模型权重继续训练，但优化器和 scaler 可重新初始化。

### 多 Seed

`run["seed"]` 应支持整数或整数列表。即使当前为了节省计算资源只跑 `[42]`，文件命名和 metrics 也必须带 seed，避免未来多 seed 实验混淆。典型命名包括：

```text
[model_alias]seed42train.jsonl
[model_alias]seed42valid.jsonl
[model_alias]seed42summary.json
```

最终 eval 应支持按 seed 记录单次结果，并可按 model 聚合多 seed 均值。

### Attention 机制

固定硬阈值 attention 已废弃，不应再使用 `attn.name="threshold"` 作为 attention 实验组。当前保留的阈值思想实验是自适应阈值 attention，配置名为：

```text
adatre05attn
adatre10attn
```

其机制名为：

```python
{"name": "adaptive_threshold"}
```

保留条件为：

```text
attention_prob >= max(
    length_scale / 当前可见上下文长度,
    relative_threshold * 当前 query 的最大 attention_prob
)
```

默认两组为：

```text
adatre05attn: relative_threshold=0.05, length_scale=1.0
adatre10attn: relative_threshold=0.10, length_scale=1.0
```

该机制不进行排序，不使用 `topk`，主要用来比较“自适应阈值稀疏 attention”是否能在较低额外计算成本下接近或优于 top-k attention 的 SAE 分析效果。

### 日志格式

控制台日志必须使用固定列宽输出，保证不同模型名、step、loss、事件信息长度不同的时候，`|` 分隔符仍然纵向对齐。普通训练日志和事件日志必须共用同一套列宽。

普通训练日志示例：

```text
[train]  | GPU2   | top16attn s42                  | step=2000                | train_loss=5.44                | valid_loss=6.32    | time=29s/85s       | mem=237.3/503G   | vram=8.4/45G
```

事件日志示例：

```text
[train]  | GPU1   | base s42                       | checkpoint exists        | step=40000 >= max_steps=40000  |                    |                    |                  |
[train]  | GPU2   | top16attn s42                  | best_step=1000           | best_valid_ce_loss=6.28        |                    |                    |                  |
```

资源标签统一使用 ASCII 的 `mem` 和 `vram`，避免服务器终端中文编码异常。

### Metrics

按 step 产生的训练、验证、SAE、attention、FFN 指标优先保存为 JSONL，每行一个事件或 step。最终汇总保存为 JSON。评估阶段可覆盖低成本图表和 summary，但训练 checkpoint 不应被评估阶段保存或覆盖。

## Metrics

`metrics/` 中的指标优先使用结构化文件保存。训练和评估过程中按 step 产生的指标适合保存为 `.jsonl`，每一行对应一个 step；最终汇总结果适合保存为 `.json`。

```text
metrics/
    train.jsonl
    valid.jsonl
    sae.jsonl
    summary.json
```

## 评估与可视化

评估阶段应尽量生成图表来说明结果，而不仅保存原始数值。图表的目标是帮助比较不同模型或不同机制变体之间的差异，因此可视化应尽量合并同类项，避免生成大量细碎、难以对照的单图。

生成图表时，优先按照“同一个 SID、同一个指标、不同模型”进行合并：如果多个模型在同一个 SID 上都有同一项指标，应将它们画在同一张图中，方便直观比较不同模型在该指标上的差异。只有当指标含义不同、SID 不同或合并后图表过于混乱时，才拆分成多张图。

评估图表可以保存在对应任务的 `eval/` 或 `metrics/` 目录下；如果图表主要用于人工查看和比较，优先放在 `eval/` 中。
